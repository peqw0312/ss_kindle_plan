# 第 4 步 · 排障手册

按「你看到的现象」查，不用从头读。

---

## 先做这三件事（90% 的问题在这里就能定位）

### ① 先用浏览器打开那个图片地址

**主地址在云端时**（`config.sh` 里 `DASHBOARD_URL` 是 `https://…`）：

```
https://<你的>.app.workbuddy.host/health      ← 状态 JSON，最直接的证据
https://<你的>.app.workbuddy.host/dashboard.png
```

**主地址在局域网时**（`http://`）：

```
http://192.168.31.158:8000/dashboard.png      ← 换成你电脑的 IP
```

- **能看到图，且内容是新的** → 问题在 Kindle 端或网络，看 [B/C/D 区](#b-屏幕与显示)
- **打不开 / 一直转圈** → 出图那边的问题，看 [E 区](#e-电脑端生成与托管)
- **能打开但内容是旧的** → 先看 `/health` 的 `next_build_at` 是不是未来时间（是的话说明"还没到下一个出图点"，正常）；再看本机的定时任务在不在跑

这一条能立刻把问题范围砍掉一半，务必先做。

> **走云端就顺手看一眼 `/health`**：`ok: true` 说明出图正常，问题在 Kindle 那边；
> `ok: false` 的话 `reason` 里直接写着原因（上游接口挂了、字体没找到等等）。
> 服务不会因为出图失败而停摆 —— 它会继续发上一张好图，`age_seconds` 会一直涨。
>
> **注意`age_seconds` 一直涨本身不是故障**：一天只出四次图，它涨到下一个
> 时刻点才归零。判断"是不是卡住了"要看 `next_build_at` —— 它必须是个未来时间。

> **走局域网时用手机测最准** —— 手机走的是和 Kindle 一样的无线网，
> 能顺带验证「是不是电脑的防火墙拦了」。

### ② 在 Kindle 上跑一次单次刷新

KUAL → AI 信息屏 → **「⟳ 测试下载并刷新一次（排障用）」**

它会打印每一步的结果（`[1/6]` WiFi、下载返回码、文件头、**设备时间对表**、
写屏、**贴时钟**，最后是设备状态）。**卡在哪一步，问题就在哪一步。**

### ②' 时钟相关的问题，单独跑这个

KUAL → AI 信息屏 → **「🕐 时钟贴图自检」**

只验"Kindle 能不能把时钟贴到指定位置"这一件事 —— 这是唯一一个**没法在电脑上验**
的环节（`eips -x/-y` 在老固件上支持不一）。时钟空白、位置不对，都先跑它。

### ③ 看日志

KUAL → AI 信息屏 → 「☰ 查看日志」，或者 USB 连电脑看
`extensions/aistatus/aistatus.log`。

## A. Kindle 脚本跑不起来

### 点「启动」没反应，屏幕也不变

先确认它到底有没有跑起来 —— 看 `/mnt/us/extensions/aistatus/.running` 这个文件在不在。

不在的话，检查这几条：

| 检查项 | 怎么查 |
|---|---|
| 脚本有执行权限吗 | SSH 进去 `ls -l bin/`，没有 `x` 就 `chmod +x bin/*.sh` |
| 目录层级对不对 | 必须是 `/mnt/us/extensions/aistatus/config.xml`，不能多套一层文件夹 |
| config.xml 有没有被改坏 | 必须是合法 XML；`<id>` 和文件夹名都应该是 `aistatus` |

### 报 `not found` / 各种莫名其妙的语法错误

**99% 是换行符问题。**

在 Windows 上编辑过的 `.sh` 会变成 CRLF 换行，Kindle 的 shell 解析不了，
报错信息还完全指不到根因。

```bash
# 检查
file bin/start.sh          # 应该显示 "ASCII text"，如果显示 "with CRLF line terminators" 就是它
# 修复
sed -i 's/\r$//' bin/*.sh config.sh
```

项目里的 `.gitattributes` 已经强制了 LF，但**通过 USB 手动拷贝时不会经过 git**，
所以电脑侧的编辑器有可能把它转成 CRLF。用 VS Code 的话右下角能看到换行符类型。

### KUAL 里看不到「AI 信息屏」这一项

1. 确认 `extensions/aistatus/config.xml` 存在
2. 确认 `menu.json` 是合法 JSON（用在线 JSON 校验器过一遍，中文引号、多余的逗号都会让它失效）
3. KUAL 本身有缓存，**重启一次 Kindle** 最省事

### 点了「启动」当时好了，过一会又恢复成书架界面

说明主循环退出了。看日志最后几行找原因，常见的是：

- `STOP_FRAMEWORK=0` 时系统屏保把画面盖掉了 → 改成 `STOP_FRAMEWORK=1`
- 主循环被 KUAL 回收了 → 确认 `start.sh` 用的是 `nohup ... &`（项目里已经是）

## B. 屏幕与显示

### 右上角时钟那块是空白

先看 Kindle 启动日志里这一行：

```
时钟：本机贴图**未就绪** —— 缺 /mnt/us/extensions/aistatus/clock/clock.conf
```

看到它基本就确诊了：**`clock/` 目录没拷全**。整个目录约 4 MB / 1441 个文件，
用 USB 拷的时候如果只挑 `.sh`、或者中途断过，就会少文件。

```bash
# SSH 进去数一下，应该是 1440 张 png + 1 个 clock.conf
ls /mnt/us/extensions/aistatus/clock/*.png | wc -l
```

不是 1440 就重拷整个 `clock/` 目录。

> **也有可能你压根没生成过**：`clock/` 是电脑上用
> `python dashboard/tools/make_clock_assets.py` 生成的，约半分钟。
> 生成完再拷。

### 时钟跑到屏幕左上角去了

说明这个固件的 `eips` **不支持 `-x / -y`**（贴到指定坐标）。

跑一次 KUAL → **「🕐 时钟贴图自检」** 确认 —— 那支脚本专门验这件事，
它会一步步告诉你时钟出现在哪、以及该怎么改。

确诊之后两种选法，**都要改两个地方**：

```yaml
# 电脑上 dashboard/config.yaml
clock:
  mode: image        # ← 改回画进图里
```
```sh
# Kindle 上 config.sh
CLOCK_MODE=off       # ← 不贴
```

改完重新发布云端的 `dashboard/`，并把新图拉到 Kindle。
代价是时钟精度退化到"跟整图刷新走"（一天四次），页脚那行时间戳会是唯一的参照。

### 时钟位置偏了一点，像"另一块拼上去的"

**在电脑上跑这个，它专门查这件事**：

```bash
python dashboard/tools/layout_check.py
```

看最后那段【时钟精灵图 · 与版面几何同步】。它会比对：

- `clock.conf` 里的坐标 vs 按**现在**的配置算出来的坐标
- 精灵图的尺寸、张数、以及一个把「字号 + 样式 + 字体 + 矩形」都算进去的指纹

对不上就重跑 `make_clock_assets.py`，再把整个 `clock/` 重拷进 Kindle。

> **这个故障最阴的地方**：电脑上打开 `docs/dashboard.png` 看是完全正常的
> （因为留白区本来就是白的），只有真机上才能看出时钟位置不对。

### 线上 `/health` 的 `clock_region` 和本机 `clock.conf` 差 1px —— 正常吗？

**正常，不用管。** 线上实测 `[645, 18, 1030, 129]`，本机是 `[644, 18, 1030, 129]`。

原因是出图和生成精灵图用的**不是同一个字体文件**：

- 本机解析到 `Noto Sans SC`（独立 `.otf`）
- 云端解析到 `Noto Sans CJK SC`（`.ttc` 字体集合）

两者字形度量差 1px，而留白区的左边界 = 右边界 − 时钟字宽，所以就差了 1px。

**为什么无害**：精灵图左侧本来就有若干列纯白内边距，云端那一列也是空白 ——
逐像素量过，两边在 `x=640..650` 全列都是纯白，属于**白压白**，屏幕上看不出来。

```bash
# 想自己确认一遍就这么跑，它会把两边的坐标和差值打出来
python dashboard/tools/check_cloud.py --url https://<你的>.app.workbuddy.host
```

它把 `≤2px` 判为一致。**超过了才是真故障** —— 那说明两边字体或字号不是一套了，
精灵图会盖到别的字上或者露一条白缝，去重跑 `make_clock_assets.py` 并把
`clock/` 重拷进 Kindle。

### 时钟的字和图上其他字"不同款"

同上面那条，看 `layout_check.py` 输出的**指纹**那一行，它会打印精灵图实际
用的是哪个字体。正常的应该是 `Noto Sans SC Bold` 之类。

如果你电脑上 `config.yaml` 的 `clock.font` 是空的、或者路径写错了，
本机会退回微软雅黑 —— 而云端出图用的是 Noto Sans CJK，两者行高差 10px。
`make_clock_assets.py` 遇到"配置指了路径但文件不存在"会**直接报错停下**，
不会偷偷用别的字体；但"配置压根是空的"这种它没法拦，只能靠这条自检。

### 屏幕上的时间不对（整体错几小时）

时钟由 Kindle **自己的系统时间**画，所以设备时间错了屏幕就错。

跑 `refresh.sh`，看 `[4/6] 设备时间对表` 那一段：

```
[4/6] 设备时间对表…
      服务器 2026-09-18 17:52:41
      设备   2026-09-18 09:52:40   偏差 28801s
      !! 偏 28801s。时钟由本机画，偏多少屏幕上的时间就错多少。
```

三种情况：

| 偏差特征 | 多半是 |
|---|---|
| 差**整小时**（如 28800s = 8 小时） | 设备时区不是 `Asia/Shanghai`。设置 → 设备选项 → 设备时间 |
| 差几百到几千秒 | 设备时钟漂移。`CLOCK_SYNC=1` 会自动用服务器时间校准 |
| 差几天到几年 | 设备从没对过时。校准一次就好 |

正常情况 `CLOCK_SYNC=1` 会自己修，日志里会写「校准成功，设备时间现在是 …」。

**如果校准失败**，日志里会有：

```
!! 校时失败：这个固件的 date 不接受 epoch。已停止重试。
```

有些老固件的 `date -s` 语法不一样（脚本已经试了 `@epoch` 和裸 epoch 两种）。
这种情况下最省事的办法是：

1. `STOP_FRAMEWORK` 改成 `0`
2. 启动一次信息屏，让原生界面起来，它会自己联网对时
3. 对完再改回 `1`，重启信息屏

> **顺带一提**：设备时间错得离谱时，`curl` 连 https 会报返回码 35/60
> （TLS 握手失败），看起来像"证书问题"，其实是时间问题。所以 `[4/6]`
> 排在下载之后、显示之前 —— 下载能通说明时间还没离谱到那个程度。

### 画面错位 / 只显示一部分 / 花屏

**分辨率不对。** `eips -g` 只认原生分辨率的图。

在 Kindle 上跑 KUAL → 「ⓘ 查看设备信息（取分辨率）」，看 `eips -i` 输出的
`xres` 和 `yres`，然后回去改 `dashboard/config.yaml`：

```yaml
device:
  model: kindle_pw3     # 或者直接写死：
  # width: 1072
  # height: 1448
```

**Paperwhite 3 是 1072 × 1448。** 如果 `eips -i` 显示的是别的数字，以它为准。

### 残影越来越明显（上一屏的字隐约还在）

墨水屏局部刷新的固有问题。把全刷频率调高：

```sh
# Kindle 端 config.sh
FULL_REFRESH_EVERY=3      # 每 3 次局部刷新就全刷一次
# 或者设成 1，每次都全刷（画面会闪一下，但最干净）
```

### 屏幕一片空白 / 只有一点字

如果字是「电量不足」之类的提示 → 那是**正常行为**，说明电量低于
`LOW_BATTERY_THRESHOLD`，接上充电器就好。

如果什么都没有 → 跑一次 `refresh.sh` 看卡在哪。

### 画面正常但角落有一行乱码文字

那是 `SHOW_STATUS_LINE=1` 画的状态行。位置按「字符单元」算，
不同固件栅格不一样，会飘。**用不到就关掉**（设 0），或者自己调 `STATUS_ROW`
试到合适位置。

## C. 下载失败

`refresh.sh` 会**把主地址和备用地址各试一次**，每个都打印 curl/wget 的返回码，
对照这个表：

| 返回码 | 含义 | 处理 |
|---|---|---|
| `0` | 成功 | 如果文件头不对，看下一条 |
| `6` | 域名解析失败 | WiFi 没通，或者 DNS 有问题。先确认能打开别的网页 |
| `7` | 连不上服务器 | 网络受限，试试换 `WIFI_TEST_IP`，或者手机热点 |
| `28` | 超时 | 网络太慢。把 `HTTP_TIMEOUT` 调大到 120 |
| `35` | TLS 握手失败 | **设备时间不对**。Kindle 时间错会导致 HTTPS 全线失败，去设置里校准 |
| `60` | 证书不受信任 | 同上，先校准时间；校准后还报就换 http 的局域网地址（见下） |

> **`35` / `60` 和时钟有个连带关系**：时钟改由 Kindle 本机画之后，
> 设备时间对不对变得比过去重要得多（屏幕上的时间直接由它决定）。
> 服务器每个响应都带 `X-Epoch` 头，`CLOCK_SYNC=1` 会拿它自动校准设备时间 ——
> 所以正常情况这个坑会自愈。校准失败的样子和处理见
> [B 区 · 屏幕上的时间不对](#屏幕上的时间不对整体错几小时)。

### 报 `certificate error` / 返回码 `60`

**这是走云端时最可能遇到的一种**，而且原因很实在：2015 年前后的 Kindle 根证书库偏旧。

处理方法有优先级：

1. **先校时**：Kindle 设置 → 设备选项 → 设备时间，手动同步一次。时间偏差太大会让
   本来没问题的证书也验不过。
2. **还是不行就换本机**：把 `config.sh` 里 `DASHBOARD_URL` 和
   `DASHBOARD_FALLBACK_URL` 的**值对调**，`WIFI_TEST_IP` 同时改回网关
   （`192.168.31.1`），让它走 `http://` 的局域网地址。

> 实测云端域名是 **TLS 1.2 + DigiCert 签发**，证书链完整，PW3 正常固件应该认。
> 所以这一条更像是保险丝，而不是预期故障。

### 文件头不是 `89504e47`

说明下下来的不是 PNG，而是服务端的一张错误页（404 / 5xx）。

**走云端**：多半是链接写错了。地址应该是 `…/dashboard.png`，不是站点首页。
用电脑打开 `…/health` 看服务是不是正常的。

**走局域网**：常见原因有

- `DASHBOARD_URL` 少了 `/dashboard.png`（只写到 `:8000/` 就会拿到网页版 index.html）
- 电脑上的 `serve.py` 没在跑
- 图片还没生成过，`docs/dashboard.png` 不存在

`refresh.sh` 会把前 200 字节内容打印出来 —— 如果看到 `<!DOCTYPE html>`，
那就确诊了。让 `curl -I` 或浏览器开发者工具看一下响应头里的 `Content-Type` 也能确认。

### `wget: not found` 或 `curl: not found`

Kindle 固件版本不同，预装的下载工具不一样（有的有 curl，有的只有 wget，有的两个都有）。

项目里的 `download_image()` 已经会自动探测可用的那个。如果**两个都没有**，
检查一下是不是有人精简过系统文件。跑「ⓘ 查看设备信息」最后会列出可用的下载工具。

### Kindle 连不上电脑上的服务

按这个顺序查（从最常见开始）：

| 检查项 | 怎么查 |
|---|---|
| **防火墙拦了 8000 端口** | 最常见的。第一次跑 `serve.py` 时会弹窗，**要选「允许」**。已经点过取消的去 Windows 防火墙 → 允许应用通过防火墙，放行 Python |
| 两台设备不在同一个网段 | Kindle 连的 WiFi 和电脑是不是同一个路由器？访客网络 / 5G 和 2.4G 分属不同子网的情况也有 |
| 电脑 IP 变了 | `serve.py` 启动时会打当前 IP，和 `config.sh` 里写的一致吗 |
| 电脑睡了 | 第 4 节说的睡眠设置；电脑睡着时服务也一起停了 |
| 客户端隔离 | 有些路由器和「访客网络」默认开启 AP 隔离，同一个 WiFi 下设备之间也互相不通。关掉它 |

> **先排除防火墙**，这一条占了绝大多数。判断方法：关掉 Windows 防火墙试一次，
> 通了就是它。别长期关着，去加一条入站规则放行 8000 端口。

### 怎么确认电脑那边的服务是好的

在**电脑自己**上打开 `http://127.0.0.1:8000/dashboard.png`：

- **电脑上能开、Kindle 上不能** → 一定是网络/防火墙问题（服务本身是好的）
- **电脑上也开不了** → `serve.py` 没在跑，或者端口被别的程序占了

## D. WiFi

### `cmState` 显示 connected，但 ping 不通

`cmState` 只说「关联上了 AP」，不代表真的能通（可能需要门户认证）。

**`WIFI_TEST_IP` 该填什么，完全取决于你的主地址在哪：**

| 主地址 | 填什么 | 为什么 |
|---|---|---|
| 云端（https） | 外网地址，如 `223.5.5.5` | 要能出网才拿得到图 |
| 本机局域网 | 路由器网关，如 `192.168.31.1` | 只需要够得着家里网络，不用出网 |

```sh
# 走云端（默认）
WIFI_TEST_IP="223.5.5.5"
# 走本机局域网
WIFI_TEST_IP="192.168.31.1"     # ← 改成你的默认网关（ipconfig 里看）
```

网关也不通的话，说明根本没连上这个 WiFi，去 Kindle 设置里重连一次。

> **填错的后果是"错误的安慰"**：填了网关却走云端，它会告诉你"网络正常"，
> 然后 `[2/6]` 下载失败 —— 让人以为是地址写错了，其实是没有外网。
> 反过来填了外网地址却走局域网，家里一断网就停止刷新，哪怕局域网和电脑都好着。

### 需要网页认证的 WiFi（酒店、校园网、部分企业网）

**这个方案不支持。** Kindle 没法自动完成门户认证。
用家里的 WiFi 或者手机热点。

### 每次刷新都要等很久

正常。WiFi 重连本身要几秒到十几秒，`WIFI_TIMEOUT=90` 是给网络差的环境留的余量。
如果家里网络很好，可以把它改成 30 让失败更快暴露出来。

**如果设了 `WIFI_SLEEP=1`**，每轮都要重新连一次，会更慢（但更省电）。
网络不稳的话建议保持 `0`。

## E. 电脑端（生成与托管）

这一节对应「图出不来、或者出来了但 Kindle 拿不到新图」的各种情况。
先确认你走的是哪条路 —— **云端和本机的排查顺序不一样**。

```
方案 A · 云端
  app.py（抓数据 + 排版 + 发出去，全在一个进程里）
        │
        ▼  https://…/dashboard.png ──→ Kindle

方案 B · 本机
  generate.py  ──→  docs/dashboard.png  ──→  serve.py  ──→  Kindle
   （出图）            （文件）              （发出去）       （来拿）
```

### 云端出图不正常

先开这个地址，它是排障的唯一入口：

```
https://<你的>.app.workbuddy.host/health
```

| 字段 | 正常的样子 | 不正常说明什么 |
|---|---|---|
| `ok` | `true` | `false` 时 `reason` 直接写着原因。**服务不会因此停摆**，会继续发上一张好图 |
| `next_build_at` | 一个**未来**的时间点 | 落在过去 → 后台刷新线程卡住了，重新发布一次 |
| `age_seconds` | 会一直涨，到下一个时刻点归零 | **别拿它当告警**：一天只出四次图，涨几个钟头是正常的。真正的判据是上面那个 `next_build_at` |
| `schedule` | `00:05、05:10、12:00、15:05（Asia/Shanghai）` | 如果括号里写着「已退回本机时区」，说明云端没有 IANA 时区库 —— 容器跑 UTC 时时刻会整体偏 8 小时 |
| `clock_mode` | `local` | 是 `image` → 云端还是把时钟画进图里，那就得靠 `refresh_at` 足够密才准 |
| `clock_region` | `[644, 18, 1030, 129]` | 和 Kindle 上 `clock/clock.conf` 里的 `CLOCK_X/Y/W/H` 对不上 → 时钟会贴偏，见 [B 区](#时钟位置偏了一点像另一块拼上去的) |
| `fonts` | 含 `SC` 或 `CJK` | 写着 `DejaVu` 之类 → 中文会显示成方块 □□□ |
| `quotes_valid` / `quotes_total` | 相等 | 小 → 行情源降级了，看下面「数据是由哪来的」 |
| `weather_source` | `和风天气` | 一直是 `Open-Meteo` → 和风的 Host / Key 没生效 |

`reason` 里几种常见内容：

| `reason` 里出现 | 含义 | 怎么办 |
|---|---|---|
| `没配和风天气的 API Host / Key` | 云端没有你本机的环境变量 | **Key 必须写进 `dashboard/config.yaml`**，云端读不到环境变量 |
| `ConnectionError` / `Timeout` | 云端抓不到上游接口 | 上游抖动会自愈；持续出现就怀疑接口改了 |
| `KeyError` / `AttributeError` | 代码 bug | 看紧跟着的 `trace` 那几行 |

> **改完 `dashboard/` 里的代码要重新发布一次**，线上才会变。
> 只是数据在变的话不用管 —— 云端按时刻表自己重算。
>
> **注意：`clock_region` 变了就必须重新发布 + 重新生成精灵图。**
> 改了字号、`clock.style` 或字体的后果就落在这一个字段上。

### 本机图片根本不再更新了

按顺序查这四步，基本一步就能定位：

1. **计划任务还在吗**
   ```bash
   python dashboard/tools/install_task.py --status
   ```
   看 `返回码`：**0 = 成功**。别的数字去「任务计划程序」里看详细原因。
   状态如果是 `Disabled`，右键启用。

2. **文件的时间戳是新的吗**
   看 `docs/dashboard.png` 的「修改时间」。是几小时前的 → 任务没在跑。

3. **电脑睡了没有**
   这是最常见的原因。Windows：设置 → 系统 → 电源 →「睡眠」改成 **从不**。
   电脑睡着的时候，定时任务和 `serve.py` 都跟着停了。

4. **手动跑一次看报什么错**
   ```bash
   python dashboard/generate.py -c dashboard/config.yaml
   ```
   能跑通就说明是定时任务的问题（第 1 步），跑不通就是数据源的问题（看下面几条）。

> **注意**：图不更新的时候，Kindle 那边**不会报错** —— 它照样能把旧图下载下来
> 显示上去。所以「屏幕正常但内容没变」不代表链路健康，别被这个骗了。

### 任务计划程序里说跑成功了，但图没变

看 `--status` 的返回码是不是 0，再看时间戳。如果返回码 0 而文件没变，
多半是**渲染超了 `ExecutionTimeLimit`（30 分钟）被掐掉**——正常一次只要几秒，
真出现这种情况说明某个数据源卡住了，看日志里卡在哪一步。

### 数据是由哪来的、为什么降级了

```bash
python dashboard/tools/probe_sources.py
```

它会逐个源打印命中情况，包括天气各家的对比。日志里也能看：

- `天气：和风天气` / `天气：Open-Meteo` —— 页脚也会如实写这一轮用的哪个源
- `行情源 tencent：命中 3/3` —— 数字是「拿到几家 / 一共几个品种」

### 速览右上角写着「标题直出」

**这是降级模式，不是故障**，但有几种原因值得排查：

| 原因 | 怎么确认 | 处理 |
|---|---|---|
| 模型接口连不上 | 日志里搜「HTTP 403」或「HTTP 404」 | 检查 `digest.endpoint` / `digest.model` 填对没有 |
| 触发限流 | 日志里搜「HTTP 429」 | 降低生成频率，或换个模型 |
| 模型返回格式没解析出来 | 日志里搜「模型返回结构异常」 | 一般会自动兜底成松散解析；持续出现就换个模型试试 |

> **速览默认是关的**（`digest.enabled: false`）。如果你没开过它，屏幕上根本不会
> 出现这一块 —— 上面写的是你手动打开之后的情况。
>
> 顺带一提：原来的 `digest.endpoint` 指向 **GitHub Models**
> （`models.github.ai`），需要 GitHub token。既然这个项目已经不走 GitHub 了，
> 想开速览的话得先确认这条路在你这台机器上通，或者换一个国内的模型接口。

**降级不等于坏掉** —— 屏幕上依然有真实的新闻标题（每栏目一条），只是没有 AI 重写过的摘要。

### 行情显示成 `--`

说明三个数据源都没拿到这个品种。

```bash
# 在本地跑，看是哪个源挂了
python dashboard/tools/probe_sources.py --only quotes
```

它会逐个源打印命中情况。常见的几种：

- **代码写错**：`sh600519` 写成 `SH600519`（大小写其实没关系，但 `600519` 前面少字母、
  位数不对就会失败）
- **个股停牌 / 退市**
- **基金不在交易日**：基金显示的是当日估值，非交易时段会是空的

> Yahoo Finance 在国内网络直连基本都是 403，这是**预期行为**，它是给境外 IP 兜底用的。
> 只要腾讯或新浪任意一个命中就正常。

### 合约价格后面写着「Bitget 不可达」

> **先说一句**：合约默认是**没开的**（`quotes.items` 里只留了三个指数）。
> 这一条是给你手动加回 `bitget:BTCUSDT` 之后看的。

加密合约走的是独立链路，按 **Bitget → Gate → HTX** 依次降级，
屏幕上会如实标出这一轮用的是哪家。

- **`api.bitget.com` 在国内直连会被重置连接**，落到 Gate 是**正常的**，
  不是故障。实测 Gate 在国内 0.2 秒就通。
- **三家全挂**：只在 Bitget / Gate / HTX 同时不可达时出现，合约那两条会显示 `--`。
  这是可以接受的降级——指数和股票不受影响。

想加合约品种：

```yaml
quotes:
  items:
    - { code: bitget:BTCUSDT, name: BTC永续 }
```

`USDT` 结尾的都支持（三家接口口径一致），不支持杠杆倍数、交割合约这类写法。

### 农历或节气日期不对

农历、节气、干支、宜忌全部是**本地推算**的，不联网、不用任何第三方库，
所以"过期"这种情况不会发生。但历史上确实踩过两个坑（ΔT 分段多项式的覆盖范围、
节气时刻跨零点取整），都已经修掉并且有回归测试：

```bash
pip install lunar_python     # 只在对拍时需要，不是运行依赖
python dashboard/tools/verify_lunar.py
```

它会拿 lunar_python（寿星天文历体系）对拍 3000 个随机日的农历/干支/建除、
218 年的春节、以及 2020-2035 逐日节气。**全绿就说明模块没问题。**

如果排出来的日期整体差一天，先确认**系统的时区是 `Asia/Shanghai`**——
节气时刻是按北京时间切日的，服务器跑在 UTC 上会整体错位。

看某一天的完整信息：

```bash
python dashboard/tools/verify_lunar.py --list 2026-10-01
```

### 想改版式，又怕把内容挤没了

版式是"预算问题"：1448px 里要放日历条、天气、3 条行情和页脚。
改字号或内边距之前先跑：

```bash
python dashboard/tools/layout_check.py
```

它会量四样东西，都是**踩过坑才加进来的**：

1. **纵向预算** —— 五张场景（平时 / 节日 / 节气 / 春节 / 预警）各占多少像素、余量多少，
   预览图写到 `.workbuddy/_preview/`
2. **日历条横向预算** —— 12 小时制的「晚上 11:59」比 24 小时制宽得多，
   没按最宽形态预留就会在晚上压到农历上
3. **天气卡片横向预算** —— 数据格会不会挤到隔壁格、描述会不会压到数据格上
4. **时钟精灵图与几何同步** —— 这一项是**唯一一个"改字号会导致屏幕出错"的连带后果**：
   时钟区的矩形变了而精灵图没重新生成，真机上就会贴偏。电脑上看预览图完全正常，
   所以必须靠这个自检拦。它比坐标、张数、尺寸、字体指纹四样

**余量安全线是 40px。** 这条以前是因为"本机雅黑 / 云端 Noto 行高不同"而设的；
现在图上所有文字（含时钟精灵图）都由 `fonts.book_for` 统一解析，
本机和云端用的是同一套字，行高不会再漂 —— 但 40px 这个习惯保留着，
因为改字号和换字体仍然会让某些字形宽度变化，留点余量总没错。

> 这四项里前三项是**真实翻过车**的：旧版用 3 列数据格，每格 161px，
> 而「空气 轻度污染 118」要 308px，直接糊到隔壁格子上；同一版还把温度和
> 一整句描述并排，585px 的内容塞进 445px。两个问题都是"看着挺合理、
> 量一下才知道越界"，所以固化成了自检项。
> 第四项是"把时钟交给 Kindle 本机画"带进来的新风险，同样固化成了自检项。

### 中文显示成方块 □□□

电脑上没找到中文字体。

- **Windows**：自带微软雅黑，一般不会有这个问题
- **Linux**：装 `fonts-noto-cjk` 或 `fonts-wqy-microhei`，然后 `fc-cache -f`
- 或者直接指定字体文件：

  ```bash
  # Windows
  set AIINFO_FONT=C:\Windows\Fonts\msyh.ttc
  set AIINFO_FONT_BOLD=C:\Windows\Fonts\msyhbd.ttc
  # macOS / Linux
  export AIINFO_FONT=/path/to/你的中文字体.ttf
  export AIINFO_FONT_BOLD=/path/to/你的中文字体粗体.ttf
  ```

设置正确时，生成日志里会打印实际用的字体，例如：
`字体：常规=Noto Sans SC Regular / 粗体=Noto Sans SC Bold`

> **这里显示 `Noto` 而不是 `Microsoft YaHei`，是正常的、也是想要的。**
> 因为 `config.yaml` 里的 `clock.font / font_bold` 把整条管线钉到了 Noto，
> 好让**出图**和 **Kindle 上的时钟精灵图**用同一套字。
> 详情见 [第 3 步 · 时钟](03-部署方案.md) 那一节。
>
> 上面这两个环境变量的优先级**低于**配置里的 `clock.font` —— 想临时换字体，
> 改配置比设环境变量管用。

### 新闻源一堆「请求失败」

现在跑在**你自己家里**，所以这多半是网络问题，不是 IP 被拦：

- 你挂的代理是不是把国内站点也代理走了？看 `dashboard/config.yaml` 里的
  `network.use_env_proxy`，默认是 `false`（**不跟随系统代理**），故意的 ——
  国内接口被绕到境外节点，轻则变慢，重则被对方按异地 IP 拦掉
- 单个源挂了不影响别的：每个源独立容错，失败就跳过

> 速览默认是关的，所以正常情况下这一整条链路（25 个 RSS 源）根本不会跑。

### 速览少了一条（只显示两个栏目）

> 同样地，**速览默认关闭**，这一条只在你自己打开 `digest.enabled: true` 之后才适用。

版面放不下，自适应裁剪生效了。日志里会有一行：

```
! 版面放不下：速览由 3 条裁到 2 条
```

每个栏目各占一条，少一条就意味着某个栏目在屏幕上消失了。想全留下，任选一种：

- `digest.max_summary_lines: 1`（摘要只留一行，省最多空间）
- `quotes.items` 少一个品种（行情每行占约 174px）
- `weather.enabled: false`（关掉天气卡片，能让出 520px）
- `calendar.show_yiji: false`（去掉日历条底部的宜忌行）
- `calendar.enabled: false`（整个日历条去掉，但这是本项目的特色，慎重）

改完一定跑 `python dashboard/tools/layout_check.py` 确认余量，
别靠肉眼估计 —— 它用的是"最长的农历月名 + 四位数的 AQI"这类偏长输入。

### 电脑上的 Python 环境坏了 / 换了台电脑

依赖只有三个包，重装很快：

```bash
python -m venv .venv
.venv\Scripts\pip install -r dashboard/requirements.txt   # Windows
```

重装完记得把计划任务指向新的 Python：

```bash
python dashboard/tools/install_task.py    # 重新注册一遍就指向当前解释器
```
