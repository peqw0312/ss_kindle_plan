# 去掉时钟之后还剩多少刷新 · 服务器选型评估

> 结论先行：**"关掉时钟"这件事本身有个坑 —— 照现在的代码关掉它，一度电都省不下来。**
> 而且"时钟"有两种关法，代价差 360 倍。先看清楚是哪一种，再决定服务器要多大。
>
> 本文所有带"实测"的数字都是 2026-09-19 在你这台电脑上跑出来的，不是估的。

---

## 一、先修一个 bug：`CLOCK_MODE=off` 不会让心跳变慢

`bin/aistatus.sh` 里心跳间隔是这么算的：

```sh
sleep_to_next_tick() {
    tick=$(int_of "$CLOCK_INTERVAL")     # ← 无条件读 CLOCK_INTERVAL，不看 CLOCK_MODE
    ...
}
```

也就是说：**把 `CLOCK_MODE` 改成 `off`，只是不贴钟了，设备照样每 60 秒醒一次**，
唤醒次数一点没少。你按这个方向省电是白折腾。

要真省，得让心跳在不需要贴钟的时候退化到"只在要拉图的时候醒"。这个改动很小
（`sleep_to_next_tick` 里按 `CLOCK_MODE` 分流），但**必须先改，否则下面所有讨论都没意义**。

## 二、60%/晚 最可能不是"醒得太勤"，而是"压根没睡进去"

`secure_sleep()` 有一条退路：找不到 RTC 唤醒节点时，改用普通 `sleep` 循环 ——

```sh
if [ "$USE_RTC_SLEEP" = "1" ] && [ -n "$RTC" ] && [ -w "$RTC" ]; then
    echo mem >/sys/power/state          # 真休眠，CPU 断电
else
    while ...; do sleep 10; done        # ← 设备全程醒着，只是脚本在等
fi
```

**走哪条路，日志里一个字都没写**（我查过了）。所以现在的现象有两种解释：

| 猜测 | 特征 | 后果 |
|---|---|---|
| **A. 没睡进去**（走的是 else 分支） | 屏幕常亮、按电源键不用等它醒、掉电极快 | 关时钟**没用**，得先解决休眠 |
| **B. 真睡了，但 1440 次/天唤醒太贵** | 屏幕是黑的、每次醒来要等一下 | 关时钟有用 |

60%/晚（约 8~10 小时）意味着 **~6%/小时**。真休眠的 PW3 一次唤醒只花几十毫秒，
算下来一天也就 1~2%，撑不起 6%。**所以我押 A**：设备根本没睡。

**5 分钟就能验**：Kindle 上跑起来之后，用 USB 连电脑，把
`extensions/aistatus/aistatus.log` 最后几行发我 —— 我打算往日志里加一行
"RTC 可用/不可用"，加上之后一眼就能看出来。这个诊断行我还没加，加完再让你跑。

> 顺带：如果真是 A，那"双击屏幕退出"那个功能也不会生效 —— 它的判据是
> "`echo mem` 提前返回"，而 else 分支根本不执行 `echo mem`。
> 你上次试双击有没有反应？这个也能反过来印证。

## 三、"去掉时钟"其实是两个完全不同的决定

### 方案 ① 屏幕上干脆不要时间

图还是**一天 4 张**，Kindle 还是**一天连 4~5 次 WiFi**。

- 服务器负担：**和现在一模一样**，一点没减
- 省电：取决于第二节里那个 bug 修没修
- 代价：信息屏上没有时间了

### 方案 ② 把时间画回图里（像大多数同类项目那样）

要让屏幕上的分钟数是准的，图就必须**每分钟重画一张**。这才是真正的负担来源：

| | 现在（时钟本机贴） | 方案 ②（时钟画进图） | 倍数 |
|---|---|---|---|
| 服务器出图 | 4 次/天 | **1440 次/天** | ×360 |
| 上游 API 请求 | 实测 3 个/次 ≈ **12 个/天** | ≈ **4320 个/天** | ×360 |
| 服务器 CPU | 实测 0.03s/次 ≈ 12s/天 | ≈ **43s/天** | ×360 |
| Kindle 连 WiFi | 4~5 次/天 | **1440 次/天** | ×288 |
| 下行流量 | 61KB × 5 ≈ **0.3 MB/天** | 61KB × 1440 ≈ **88 MB/天** | ×288 |

**88 MB/天、2.6 GB/月** —— 免费服务器的流量包通常就是这个量级，会直接顶穿。
而且 Kindle 每分钟开一次 WiFi 射频，**比贴一张本地图贵得多**，电反而更不禁用。

> 所以：如果目的是省电，方案 ② 是反方向的。要省电就走方案 ① + 修第一节的 bug。

## 四、实测：一次出图到底要什么

在 `192.168.31.158` 这台机器上跑 `generate.collect()` + `render()`：

```
网络请求   3 个
   GET  https://api.open-meteo.com/v1/forecast          天气 + 未来几天
   GET  https://air-quality-api.open-meteo.com/…        空气质量
   GET  https://qt.gtimg.cn/q=usNDX,usINX,sh000001      三个指数，一个请求批量拿
抓数据     1.9 ~ 20.2 秒   （Open-Meteo 境外源，抖动很大）
排版出图   0.03 秒         （含 PNG 编码）
产物       59 KB
```

配了和风天气之后请求数差不多（换成和风 2 个 + 腾讯 1 个），但**境内源，延迟稳定得多**。

**没测准的一项**：进程峰值内存。我试了三种 Windows API 都没取到，不编数字。
确定的下界是那张位图本身 **1.55 MB**（1072×1448 单通道），Python + Pillow 常驻
的实际峰值要按几十 MB 估 —— 选机器时按 **≥512 MB 内存**留余量就行，这条不该是瓶颈。

### 服务器最小规格（按方案 ① / 现状算）

| 资源 | 需求 | 说明 |
|---|---|---|
| 运行时 | **Python 3.10+，能装 Pillow** | Pillow 是 C 扩展，**必须能 pip install** |
| 常驻进程 | **要** | `app.py` 自带后台线程按时刻表出图 + 内存缓存 |
| 端口 | 1 个，读 `PORT` 环境变量 | 已按这个写 |
| CPU | 极低 | 一天 4 次 × 0.03s |
| 内存 | ≥512 MB 建议 | 见上 |
| 流量 | **<1 GB/月** | 0.3 MB/天 × 30 ≈ 9 MB，加响应头余量也就几十 MB |
| 磁盘 | 不需要 | 云端不落盘，图在内存里 |
| 出网 | 能访问 `api.open-meteo.com`、`qt.gtimg.cn`、（可选）`*.re.qweatherapi.com` | 国内服务器都能到 |

**一句话：负担非常轻。** 真正的门槛不是算力，是这两条：
1. **能跑 Python 并装 Pillow**（把 Qoder Sites 那种"只能静态文件 + TS 边缘函数"直接排除掉了）
2. **有常驻进程**（把纯 serverless/函数计算排除掉了 —— 除非改成"每次请求现场出图"，
   那样一次请求要等 2~20 秒，Kindle 的 60 秒超时勉强够，但很难看）

## 五、阿里云 / 腾讯云免费额度，你需要告诉我这些

我没法替你判断额度，得看你账号里实际给的是什么。麻烦确认：

1. **是"免费试用"还是"长期免费"？** 试用一般 1~3 个月到期，到期会**直接关机**，
   你的屏就永远停在最后一张图（而且不报错）。
2. **是不是要绑卡/实名？** 绑卡这条你原来明确不要。
3. **给的形态是什么**：轻量应用服务器（有 root，随便装）／ 云函数（serverless）／
   还是只有对象存储 + CDN？—— 只有第一种能直接跑 `app.py`。
4. **带宽和月流量上限**是多少。
5. **系统能不能出网**到 `api.open-meteo.com`（部分新购云主机默认安全组限制出方向）。

**如果是轻量应用服务器（2 核 2G 那种）**：完全够用，我可以给你一份
一键部署脚本（装 Python + 拉代码 + systemd 常驻 + 开机自启）。
这种情况下 Kindle 的地址换成 `http://<你的服务器IP>:8000/dashboard.png` 就行。

**如果是云函数/Serverless**：需要改造（去掉后台线程，改成"请求来了判断该不该重算"，
缓存要么放内存要么放对象存储），能做，但要改 `app.py`，不是搬过去就行。

## 附：如果最终决定"屏幕上不要时间"

要同时改两处，少一处就是静默故障（这是项目里定过的死规矩）：

- Kindle `config.sh`：`CLOCK_MODE=off`
- 电脑 `dashboard/config.yaml`：`clock.mode: image`（把时间画进图里）**或**
  把时钟那一栏整个关掉

两者混着配的两种错法：Kindle `off` + 图 `local` = 右上角永远一块空白；
Kindle `local` + 图 `image` = 时间叠两层糊成一团。
