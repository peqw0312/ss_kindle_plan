三、两条路：一张图是怎么上屏的

A · 平时（电脑可能关着）

  1. GitHub 定时任务跑一轮 build.yml（实测 1～3 小时一次，不守时）。
  2. Actions 在美国的机器上抓和风 + 行情，跑同一份 generate.py。
  3. 产物覆盖到 screen 分支 → Pages 自动部署。
  4. 屏每分钟来取一次，取到就换、没换就不重绘。
  5. 所以屏上"更新 HH:MM"是云端出图的时刻，不是屏自己的时刻 —— 它可能比现在旧一两小时，这是设计不是坏了。

B · 你在调试台按「立刻出图」

  1. 浏览器打本机 POST /publish?skin=…（同一个协议，不用 token）。
  2. serve.py 在这台电脑上跑同一段 generate.py，实测 1.1 秒。
  3. 出完先自检：这张有没有天气那一块？没有就不发，屏上继续是云端那张好的。
  4. 有 → 记下这张的校验和，标记"这是本机刚出的"。
  5. 屏下一分钟来取，拿到它，比对校验和，不一样才重绘。
  6. 屏顺手上报"我贴的是 1105677263 49915"→ 调试台真值卡显示「和本机这张是同一张 ✓」。

四、四条不能破的规矩每一条都是踩过坑换来的

1 · 零成本不付费、不绑卡、不注册。和风要实名是你自己接受的例外。任何"要养一台服务器/一个服务"的方案先按这条毙掉。
2 · 凭据绝不进仓库仓库是公开的（屏没法带 token，只能走公开地址）。Key 只进 GitHub Secrets，或本机那个被 .gitignore 挡着的 env 文件。公开发布的 build.log 里也不能出现 —— 带 key 的参数一律打 ***。
3 · 电脑可以关掉数据来自云端。局域网只是加速器，不是替代：电脑一关，屏自动落回 GitHub，什么都不用改。
4 · 空图不出门出空白图是不会报错的。所以发图那一端必须自己查：本机这张是不是我亲手出的、有没有天气。真出过一次事故 —— 一张没凭据的测试图盖在云端好图上面，屏"没信息"了几小时。

五、插线会发生什么这是最容易把人绕晕的一节

  • 插线 = 屏变成一块 U 盘（电脑上看到 D:）。这时候屏幕点不动，任何"点一下屏"的操作都必须先拔线。
  • 正在被 ash 执行的脚本不能原地覆盖（设备是 FAT，没有 inode 那层间接）。所以顺序只能是：停止 → 插线 → 拷 → 拔线 → 启动。
  • 仓库工作副本是 CRLF，屏上必须是 LF。直接拷会把 \r 带进 shell 变量里，症状是"配置看着对、行为完全不对"。拷之前要转换。
  • config.sh 只在启动时读一次。拷完不重启脚本 = 白拷。
  • 屏睡着的时候什么都进不去：射频是关的，ping 不通、也叫不醒。以前为了省电让它睡（实测能睡满 601 秒），2026-09-29 起长期插电源，改成不睡了 —— 那一整类"屏停在旧图上几小时、日志一个字都不留"的毛病跟着没了。

六、出问题时先看哪里按这个顺序查，别从屏开始猜

症状先看这里
屏上信息旧 / 缺一块 调试台 屏上现在这张 那一行：它会说"本机发的是云端镜像 / 本机刚出的 / 硬盘上那张不发，因为…"。这一句直接指出是哪一层。
屏整个停在一张不动 局域网日志 .workbuddy/_serve.log 有没有每分钟一条来自屏的请求。一条都没有 = 屏没醒 / WiFi 掉了 / 脚本没跑，跟图的内容无关。
怀疑云端没出新图 用 api.github.com 查 run 列表和 screen/dashboard.png 的真实大小。别信这台电脑直接读到的 Pages —— 它挂着 GitHub 加速工具，会按 URL 回缓存内容（实测同一分钟报出过三种字节数）。
按了按钮像没反应 GET :8731/state，看 can_build / served / note 三个字段。按钮一律会回话，不回话就是请求没到本机。
换皮肤没生效 皮肤选择记在 screen/skin.txt（不写回 config.yaml，否则会自己触发自己）。云端那轮跑完后 build.log 第一行会写"本次用版式：…"。
