# 2026-09-18

## 把闲置 Kindle 改造成 AI 信息屏（项目主体完成）

用户需求：Kindle Paperwhite 3（第七代）改成 AI 信息屏，愿意越狱，要显示
天气+时间+日期 / AI 早报 / 股票基金行情，且**零成本、无服务器**。

### 交付内容

- `dashboard/` —— Python 渲染管线：Open-Meteo 天气、10 路 RSS、三级降级行情、
  GitHub Models 生成中文早报、Pillow 排版成 1072×1448 8 位灰度 PNG
- `kindle/extensions/aistatus/` —— KUAL 扩展，wget 拉图 + eips 直写屏幕 +
  RTC 闹钟休眠唤醒
- `.github/workflows/aistatus.yml` —— 定时生成并提交到 docs/，由 Pages 托管
- `guide/` —— 4 份文档（越狱 / Kindle 端 / 云端 / 排障）
- `dashboard/tools/probe_sources.py` —— 数据源自检工具

### 验证结果（本机实测）

- 天气 Open-Meteo ✅
- 行情：腾讯 4/4、新浪 4/4（含美股 usAAPL）；Yahoo 全 403（国内网络被拦，属预期）
- 新闻源：10 个源里 9~10 个可用，最多拿到 16 条候选
- 渲染：PNG 正确输出，中文正常（微软雅黑），shell 脚本 `bash -n` 全部通过

### 关键决策

1. 零成本 → 架构定为「GitHub Actions 生成 + Pages 托管」，家里不放任何常开设备
2. Kindle 端只认一张 PNG，用 `eips -g` 直接写 framebuffer，不开浏览器
3. 省电采用 kindle-dash 验证过的方案：`echo mem > /sys/power/state` + RTC 硬件闹钟，
   明确放弃不可靠的 `lipc rtcWakeup`
4. AI 摘要用 GitHub Actions 内置 `GITHUB_TOKEN`（`permissions: models: read`），
   零 Key、有免费额度、失败自动降级为原始标题
5. `docs/` 作为 Pages 输出目录，所以文档放在 `guide/` 避免语义冲突
6. `docs/debug.json` 加入 .gitignore —— 里面有城市坐标和自选股，公开仓库不宜提交

### 踩到的坑（已修）

- **内部代码 key 大小写**：腾讯返回 `v_usAAPL`，若内部键保留大小写，
  normalize 成 `usaapl` 后就永远查不到，美股会静默丢失
- **PIL anchor 用错**：时间用 `ls`（左对齐）画在右边界上会被画布裁掉，必须用 `rs`
- **手算行高导致重叠**：天气卡片第一版文字互相叠压，改为所有纵向位置由
  `font.getmetrics()` 推导
- **机器之心的 RSS 已下线**，/rss 返回 HTML 门禁页 → 增加 `looks_like_feed()` 识别
- **Hacker News 的 description 是 URL 转储** → 增加 `clean_summary()` 清洗

### 待用户确认

- 城市（当前配置默认杭州 30.2741/120.1541）
- Kindle 实际固件版本（必须 ≤ 5.16.2.1.1 才能用 LanguageBreak）

### 新增 / 重写

- `dashboard/aiinfo/lunar.py`（新，约 580 行）—— 零依赖农历模块：数据表 +
  Meeus 太阳视黄经算节气 + 干支/建除/宜忌/节日。1885-2100。
- `dashboard/aiinfo/render.py` —— 头部换成撕页日历条（左：日历纸；右：农历、
  干支、地点、时钟、节日/节气徽章；底部：宜忌冲煞）；速览改成栏目标签列；
  行情加合约来源标注；`wrap_text()` 加标点悬挂
- `dashboard/aiinfo/sources.py` —— 加密合约链路 Bitget→Gate→HTX；
  `fetch_news()` 改为按栏目返回 dict；`crypto_source_label()` 如实标注来源

- `dashboard/tools/verify_lunar.py`（新）—— 拿 lunar_python 对拍农历模块
- `dashboard/tools/_marks.py`（新）—— 工具脚本共用的控制台标记（GBK 兼容）

### 验证结果

- 农历：3000 随机日 × 6 字段零差异、春节 218 年零差异、2020-2035 逐日节气
  5844 天零差异（对拍 lunar_python）
- 行情：腾讯 3/3（纳指100 / 标普500 / 上证指数）；合约 Bitget 国内不通，
  Gate 命中 2/2。整轮行情耗时从 130s 降到 3.6s（快速熔断）
- 版面：1448px 里用掉 1411px，余 37px；速览 3 条全部放得下
- 端到端：`generate.py --no-ai` 出图正常，5/5 条行情有效

### 关键发现

1. **TERM_FIX 修正表原来是错的**：表里每条对应的节气时刻都在距午夜 6 分钟内
   （1896 小暑 00:02、2008 小满 23:59），说明原始解算精确到分钟，不是"算错一天"。
   上一轮修完整点取整 bug 后有 2 条过期（1896 小暑、1912 寒露）反而把日期推错了。
   重建后全表只剩 14 条，对拍全绿。
2. **Gate.io 是国内唯一稳定直连的合约源**（0.2s）；HTX/OKX/Binance/MEXC 全超时。
   但它没有 24h 开盘价字段，要用 `last - change_price` 反推昨收。
3. **连着挂的两个源会把生成拖慢 2 分钟**：加"首个 symbol 就失败 → 跳过该源"
   的快速熔断，并把合约超时从 20s 降到 8s。
4. **`*>` 和 Out-File 在 PowerShell 里写 UTF-16**，Read 判定为二进制；
   必须用 `[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`。
   另外子进程 stdout 是 GBK 时打印 ✅ 会直接抛异常中断脚本。
5. **摘要经常出现"最后一行只有一个句号"**，靠 `wrap_text()` 加标点悬挂解决。

### 实测数据（第三轮重新量的）

去掉速览净释放 **488px**。当前版面：日历条 337 / 天气 270 / 速览 488 / 行情 234 /
页脚 58 / 留白 61 = 1411（余 37）。速览是最大的一块，占屏 34%。

### 关键技术发现

- **`digest.enabled` 是个死开关**：早就写在 `config.py` 的 DEFAULTS 里，但
  `render()` 和 `collect()` 都没读它。`weather.enabled` / `quotes.enabled` 同样没生效。
  本轮要接上——"关掉速览"因此变成改一行配置而不是删代码。
- **`eips` 能力比现在用到的强得多**（MobileRead 官方文档）：
  ```
  eips -g 图.png [-w gc16|gl16|du] [-f] [-x 像素] [-y 像素] [-v]
       -w 波形，默认 gc16；-f 全刷，**默认是局部刷新**；-x/-y 是像素坐标
  eips [row] [col] string      用系统位图字体写字（字号固定且很小，做不了大字）
  eips -d l=灰度,w=宽,h=高 -x -y   直接画矩形
  ```
  **`-x/-y` + 默认局部刷新 = 可以把小图贴到屏幕任意像素位置、只刷那一块**，
  这是"Kindle 本机画时钟"能成立的全部依据。
- **风险**：`-x/-y` 在 K3/K4 上不生效（官方文档明说"does not work on K4"），
  PW3 需真机验证；`du` 波形也需真机验证。

### 定稿的施工清单

1. **日历条放大**：大字日期 98→150（改用 `textbbox()` 按**墨迹**居中，不再按
   ascent 定位，根治"偏上"）；纸宽 232→270；年月 22→30；星期 26→34；
   农历 50→64；干支/地点 26→30；徽章 27→34；宜忌 24→30

   模型；workflow 摘掉 `models: read`；代码保留可一行开回
3. **天气**：一图一符号（晴=实心圆+8 粗射线；多云=太阳被云遮左下；
   阴=单云；雨=云+3 条**竖直**粗线；雪=云+3 圆点；雷=云+粗闪电）；
   小图标 34→46px 且 130 灰→70 墨；**每个小图标补一行文字**（晴/多云/小雨）；
   主图标 80→110、温度 84→110
4. **行情**：`quotes.items` 只留 usNDX/usINX/sh000001；**单列 3 行**，行高约 90px，
   名称 40 / 价格 52 / 涨跌 40。Bitget-Gate-HTX 那段代码保留，配置不引用即不跑

   副作用：日期翻页最晚拖到凌晨 2 点，早 6 点那次一定是新日期
6. **本机时钟（方案 A）**：新增 `dashboard/tools/make_clock_assets.py` 生成

   （local / image / off）保证真机不兼容时改一行退回。云端图右上角留白给时钟，
   位置尺寸两边必须共用一个常量
7. 连带：`layout_check.py` 不再量速览；README / guide 同步（"早报 4 条""10 个源"

## 第三轮补充（同日晚）：行情压缩 + GitHub 链路实测

用户追加两个问题：「行情可以压缩一点吧空间给其他功能」「用 GitHub 刷新会不会有网络问题」。

### ① 行情高度实测（用真实 Renderer 几何函数量，不是估算）

| 排法 | 高度 | 价格字号 |
|---|---|---|

- **上一轮的 348px 给多了**，用户直觉对。单列 3 行里那一行「纳斯达克100」只用掉
  174px，而可用宽度 976px——横向浪费严重，改成三列并排更合理

### ② GitHub 刷新链路实测（重点是 ③）

| 环节 | 实测 | 判定 |
|---|---|---|
| ① Actions 出图 | 腾讯行情 0.16s，Open-Meteo 2.0s | 低 |
| ② 提交图片 | GitHub 内网 | 无 |
| ③ Kindle 拉图 | 绕代理直连 github.io **8/8 成功，0.27–0.30s**，握手 70ms | 低 |
| ④ cron 触发 | 整点最堵，社区实测延迟 5–30 分钟 | **中** |

**结论：这条链路是通的，而且稳。不要因为担心网络就换方案。**

### 踩到的坑

1. **本机 hosts 把 GitHub 全屏蔽了**：40+ 行 `127.0.0.1 github.com / github.io / ...`，
   带 `#S302` 标记（某个 GitHub 加速/屏蔽工具写的）。**不影响 Kindle**（独立设备），
   但会让本机预览失败。
   - 注意 hosts 里那行 `*.github.io` 是**字面量**，Windows hosts 不支持通配符，
     所以真实子域名 `xxx.github.io` 不受影响（实测随机子域名正常解析到
     185.199.108–111.153）
2. **本机挂着本地代理**（`HTTPS_PROXY=http://127.0.0.1:61975`，系统代理开关却是关的）。
   第一次测「github.io 通」其实是被代理掩盖了 —— **必须用 `curl --noproxy "*"` 重测
   才拿到 Kindle 视角的真实结果**。这个教训很重要
3. **jsDelivr 现在不通**：`cdn.jsdelivr.net` 实测 3/3 失败（HTTP 000，连接被中断）。
   原打算当备用图床，**此路不通，不要写进方案**
4. **cron 定在整点是个错误**：GitHub 文档明说高负载时会延迟，**整点正是最繁忙时段**。
   上一轮写的 `0 0-14,22,23 * * *` 应改成错开的时间点（如 `7 ...`）
5. GitHub 硬规则：定时任务**最低 5 分钟**间隔（`*/3` 被静默忽略）；cron **只认 UTC**；
   仓库 60 天无提交会自动禁用 schedule —— 但我们每轮都提交 docs/，**永远不触发**，是优势

### 仍待真机验证

- Kindle 老固件（2015 年 PW3）的 TLS 根证书能否认 github.io 的证书
  → 加固：`download_image()` 失败后加一次 `curl -k` / `wget --no-check-certificate`
- `eips -x/-y` 定位是否生效
- 加固项：`config.sh` 支持多 URL 依次尝试，`refresh.sh` 打印每一跳

## 第四轮：时间 12 小时制 + 换天气源 + **放弃 GitHub 改国内方案**（只调研，未动工）

### ① 天气源现状

`dashboard/aiinfo/sources.py::fetch_weather()` 用的是 **Open-Meteo**：
`api.open-meteo.com/v1/forecast` + `air-quality-api.open-meteo.com`。
免 Key、不限量、全球数值模式（约 11km）插值到给定坐标；空气质量来自 **CAMS 全球模式**；
**没有任何灾害预警字段**。WMO 天气码在 `WMO_CODES` 里映射成中文+图标。

### ② 同一时刻实测对比（2026-09-18 16:15–16:30）

|---|---|---|
| 温度 | 28.4℃ | **30.1℃** |
| 湿度 | 55% | **47%** |
| 风 | 11.5 km/h | **6 km/h（2 级）** |

### ④ 关键发现：中国天气网有可用但未公开的接口

带 `Referer: http://www.weather.com.cn/` 就能拿到 JSONP 形式的 JSON，**免 Key**：

- `http://d1.weather.com.cn/sk_2d/<citycode>.html` —— 实况（temp/WD/WS/SD/qy/njd/aqi/weathercode）
- `http://d1.weather.com.cn/dingzhi/<citycode>.html` —— 7 天预报 + **`alarmDZ` 灾害预警**
- 老接口 `http://www.weather.com.cn/data/sk/<code>.html` 已 301，不可用
- 杭州 = `101210101`。**官方数据（中国气象局），但接口未公开、随时可能变**

### ⑤ 和风天气的硬坑

- 免费订阅 **50,000 次/月**（≈1666 次/天）；我们 1 小时一次 × 3 接口 ≈ 72 次/天，占 4%
- `location` 支持**经纬度直传**（`120.2804,30.4159`），不用查城市码
- **`devapi.qweather.com` 已于 2026-01-01 停服；`api.qweather.com` 于 2026-06-01 停服。**
  现在必须用控制台下发的**专属 API Host**（形如 `xxxxx.re.qweatherapi.com`）。
  网上教程几乎都还写旧域名，照抄会失败
- 注册只要手机号/邮箱 + 免费订阅，**不用绑卡、不用实名**

- **Gitee Pages 已在 2024-07-15 正式下线**，`gitee.io` 不再签发新站。此路不通
- 本机局域网地址：**192.168.31.158**（以太网）

## 第六轮：时钟交还 Kindle 本机 + 出图改时刻表（已落地并验证）

用户要求：「时间能不能直接调用系统的，这样就不用服务器一直拉数据了，然后天气和指数
这些每天中午 12 点更新一次就行了」。经 AskUserQuestion 确认两点：
**出图时刻「把美股的时间也算上」**、**本机时钟「全天每分钟」**。

### 最终架构

**时间与出图彻底解耦**：图里时钟那块**留白**，Kindle 用**自己的系统时间**每分钟
贴一张小图；出图只在数据真的变了的时刻发生。

```
云端 app.py  一天出 4 次：00:05 / 05:10 / 12:00 / 15:05（按 Asia/Shanghai 判定）
Kindle       每分钟醒一次：只看该不该拉整图 → 贴时钟 → 睡
```

**为什么是这四个点**（每个都有理由，别删）：
- `00:05` 翻日期。不然 00:00–12:00 屏幕上还是昨天的大字日期和农历
- `05:10` 美股收盘（夏令时 04:00 / 冬令时 05:00，取两者**之后**，一年不用改）
- `12:00` 用户要的点，此时美股当日已收官
- `15:05` A 股收盘（沪深 15:00 收），不然上证整天停在 11:30 午休前的价

上游调用 96 次/天 → 4 次/天。

### 这一轮的坑（都修了，值得记住）

1. **字体漂移（最隐蔽的一个）**：时钟是**本机**生成、贴到**云端**出的图上。
   本机默认解析到微软雅黑、云端解析到 Noto Sans CJK，**行高差 10px**，
   而时钟区坐标正是用这些字量出来的 → 时钟像"另一块拼上去的"。
   本机实测两者时钟区差 `[633,18,1030,119]` vs `[644,18,1030,129]`。
   解法不是逐个调用点对齐，而是**结构性统一**：出图和精灵图都走 `fonts.book_for(cfg)`。
2. **`clock.conf` 的 CRLF（会静默贴错位置）**：`Path.write_text` 在 Windows 上
   默认把 `\n` 翻成 `\r\n`，而这个文件会被 Kindle 的 sh `source`，
   于是 `CLOCK_X="644\r"`，`eips -x` 拿到带回车的参数**不报错、只贴错位置**。
   修法三层：`write_text(..., newline="\n")` + `layout_check` 守卫 +
   Kindle 端三个脚本 `tr -d '\r'` 兜底。`.gitattributes` 也加了显式规则
   （USB 拷贝绕过 git，所以运行时兜底不能省）。
3. **云端容器跑 UTC**：时刻表若按容器本地时间判，`00:05` 会落到北京 `08:05`，
   每天上午屏幕上是昨天的日期。一律按 `location.timezone` 判定，并有专门的自检用例。
4. **Windows 没有 IANA 时区库**：`ZoneInfo("Asia/Shanghai")` 抛
   `ZoneInfoNotFoundError`（未装 tzdata）。`app.py` 捕获后退回本机时区
   （中国无夏令时，等价）并打日志 —— 否则本机试跑直接崩。
5. **`check_cloud.py` 的字体判据是个定时炸弹**：原来是
   `"CJK" in fonts or "YaHei" in fonts` 这种白名单，云端从
   `Noto Sans CJK SC` 换成 `Noto Sans SC` 后就**误报"不像中文字体"**。
   改成**排他**判据（只有 DejaVu/Liberation/Arial 这类明确不含汉字的才判错）。
6. **两个 Edit 放在同一条消息里，第一个有时静默不生效** —— 本轮又踩两次
   （`NameError: TOP_GAP`、`pretty()` 未定义）。**改成一次只改一处，改完编译/运行验证。**
7. **PowerShell 抓子进程中文输出仍会乱码**（即使设了 `[Console]::OutputEncoding`），
   结果是文件里出现「鉁?瀛椾綋」这种。数字和英文可读，够用；
   要完全干净就让 Python 脚本自己写文件（`_verify_clock.py` 就是这么做的）。

## 第八轮：用户已越狱，问怎么装 KUAL / MRPI → 发现 guide/01 §3 是过时写法

用户说「已经越狱了，怎么装 KUAL / MRPI」。核对 kindlemodding.org 的
**Legacy 段**（正对应 LanguageBreak 这一代）后，发现 `guide/01` 第 3 节写的
`mrinstaller.bin` + `Update_KUALBooklet_*.bin` + `;log mrpi` 是**更老的一套**，
当前官方流程完全不同。

### 当前官方流程（已写进 guide/01 §3）

| 东西 | 版本 | 放哪 |
|---|---|---|
| KUAL | **PEKI**（K5 及更新机型；PW3 属 K5） | 解压出的 `KUAL.sh` + `KUAL.jar` → **`documents/`** |
| MRPI | modern devices 版 | 解压出的 **`extensions/` 和 `mrpackages/` 两个文件夹** → **根目录** |

**关键认识：这一步没有任何"安装动作"**，全是往哪拷。所以失败原因只有两个 ——
放错位置，或文件名被浏览器加了 `(1)` 后缀。另外需要 **220 MB 余量**，
且腾空间前必须先开飞行模式。

### 挖到的真坑（PW3 用户实测，会白忙一下午）

**hotfix 版本必须 ≤ 2.3.7，不能用最新的 2.5.x。**
2.5.0 换了 KUAL 的签名证书 → KUAL 图标**正常出现在书库**、但一点就报
`Application Error / The selected application could not be started`，
而且**降级回 2.3.7 也修不好，只能重新越狱**。
来源：PEKI issue #10（有位 **PW3 + WinterBreak2** 用户逐字报了同样现象），
PEKI 作者确认并在 README 加了 2.3.7 上限。

### 顺带发现 guide/01 另一个漏步骤

hotfix **装完还要运行** —— 官方是两步：`Update_hotfix_universal.bin` 拷根目录 →
设置 → 更新您的 Kindle → 然后**书库里出现 `Run Hotfix` 小册子，必须点开跑一遍**。
原来文档只写了"等重启"，漏了运行那一步。
