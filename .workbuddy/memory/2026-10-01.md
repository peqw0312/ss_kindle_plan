### ★ 顺手撞出的真 bug：`config.sh` 一直是 CRLF，而 grep 骗了我们几个月

**起因**：要把 `config.sh` 拷进 Kindle 做备份，读原始字节时发现 **253 个 CR**。

**根因**：一直用 `grep -c $'\r' file` 检查换行符 —— **Git Bash 的 grep 会做换行符
转换，对 CRLF 文件报 0**。看着干干净净，实际全是 CRLF。

**为什么这次没出事**：Kindle 上那份 `config.sh` 是**纯 LF**（263 个 LF、0 个 CR），
是更早某次拷进去的、没被 CRLF 污染过。所以之前一直没暴露。

**如果拷进去会怎样**：`DASHBOARD_URLS="http://43.142.71.175/dashboard.png\r"` →
URL 尾部多个回车 → `curl`/`wget` **不报错、只是永远下不回来** → 屏停在旧图，
日志里看不出任何异常。**这正是本项目最怕的那类"只在真机才暴露"的坑。**

**已做**：
- 本机源文件修成纯 LF（CRLF 原稿备份在 `config.sh.crlf-bak`）
- 桌面副本 `C:\Users\peqw0\Desktop\config.sh` 也是纯 LF，与源逐字节一致
- `.gitattributes` 加显式规则 + 写明「`*.sh text eol=lf` 拦不住已存在的文件」
- **查 CR 的正确方法**：`ReadAllBytes` 数 `-eq 13`，**不要用 grep**

### 根因（读代码定位，不是猜）

**`aistatus.sh` 的主循环第一句就是 `refresh`，因此"启动→立刻取图"是必然的，
不取图只可能是根本没起来。** 而日志里 22:19 之后既没有 Kindle 的取图、
也没有 `/report`，最可能是 **KUAL 的「启动」没有真正跑起来**。

两个具体候选（按可能性排序）：

1. **进程压根没起来 / 起来就死了。** 最典型的原因：拷入后的 `config.sh`
   **换行符不对（CRLF）** —— 但本机那份已确认 CR=0，Kindle 上那份是更早的纯 LF 版，
   且 22:28:29 那次 `/poll.json`（只可能来自设备）说明脚本**确实跑过一轮**
   并且读到了新配置（旧配置里根本没有 LAN_POLL_URL，不可能去读 poll.json）。
   → 所以更像是**起来跑完一轮后又退出了**。
2. **第一轮 `refresh` 失败 → 600 秒重试，此后被连点/插拔打断。** 关键代码路径：
   `refresh` 失败时 `next_image_at = now + 600`，而 `secure_sleep` 里有
   `[ -f "$STOP_FLAG" ] && return 0` → **`.stop` 文件残留会让它立刻退出**；
   `trap ... TERM INT` 又会被拔 USB 打断。`init()` 里虽有 `rm -f "$STOP_FLAG"`，
   但那是在进程成功启动的前提下才生效。
3. 次要：KUAL 的「停止信息屏」→「启动信息屏」之间若**没等界面恢复干净**，
   `initctl stop framework pillow statusbar webreader` 的连坐可能把启动链一起带走。

### 结论

- **❌ 设备尚未成功上报。** `device_state.json` 全空 = 「下载 → 刷屏 → 上报」整条链
  从 22:18:59 之后**一次都没走完**。
- 唯一证明设备活过 22:19 的证据是 **22:28:29 的 `GET /poll.json`**——说明进程短暂活过
  且用的是新配置，但**它没有在那一轮走到取图**（正常顺序是 refresh → poll，
  而这里只有 poll，反过来说明那一轮很可能走的是 `plan_next_image` 里读 poll 的分支、
  而 `refresh` 判定"图没变"跳过了重绘……但那样也会调 `report_state 1`）。
  最省事的解释仍是**进程没稳定跑住**。
- **服务器侧一切正常**，不是服务端问题。
